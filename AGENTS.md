# POSE FIGHT — AGENTS.md (source of truth for every human and AI agent)

> **Read this file completely before touching anything.** Then read your workstream doc in
> `docs/agents/`. If something here contradicts a workstream doc, this file wins.

Tagline: **"Your body is your controller."**

POSE FIGHT is a mobile-first, online 1v1 fighting game. Each player uses their own phone.
Instead of buttons, players strike a **physical pose** in front of their camera. The pose is
classified **on-device** into a game move, submitted secretly, and once both players lock in,
both phones reveal the **real photos** of both players and play a **cinematic 2D fight** in
Phaser showing the result.

```
REAL PERSON → REAL POSE → GAME MOVE → SECRET SUBMIT → REVEAL (photos) → CINEMATIC 2D FIGHT
```

Feel: party game × fighting game × rock-paper-scissors × anime/arcade presentation.

This is a **4-hour hackathon**. Everything is optimized for shipping a polished demo.
Simple and reliable beats production-grade. Presentation beats complexity.

## 4. Game loop

```
LOBBY
  P1: CREATE BATTLE → ROOM CODE "K7DX" (+ QR / deep link /room/K7DX)
  P2: JOIN with code
  both: nickname + fighter (BOXER | SAMURAI | WIZARD)
  → host presses START (or auto-start when both ready)

ROUND n (repeat until KO)
  CHOOSE YOUR MOVE            ← both phones, simultaneously
  countdown 3 · 2 · 1 · POSE! ← camera preview, on-device pose classification
  📸 snapshot                 ← PoseResult + photo Blob
  MOVE LOCKED ✓               ← submitted to Convex. Opponent sees only "locked", never the move
  (waiting for opponent…)
  REVEAL                      ← both photos side by side, move names, POWER/DEFENSE numbers
  3 · 2 · 1 · FIGHT!
  CINEMATIC FIGHT (Phaser)    ← both phones play the same CombatResult
  HP bars update
  → next round   or   KO → WINNER SCREEN → rematch / new room
```

Combat is **resolved once, on Convex**, when the second move arrives. Clients never compute damage.
Full rules: `docs/GAME_DESIGN.md`.

## 5. Architecture

Three independent systems connected by two data contracts:

```
CAMERA ──► VISION ──PoseResult──► MULTIPLAYER (Convex) ──CombatResult──► GAME (Phaser)
```

| System | Owns | Knows nothing about |
|---|---|---|
| **VISION** | camera, MediaPipe PoseLandmarker, geometry, classification, countdown, snapshot, debug overlay | Convex, Phaser |
| **MULTIPLAYER** | rooms, players, rounds, secret submissions, photo storage, authoritative combat resolution, realtime sync, app screens/routing | MediaPipe, Phaser internals |
| **GAME** | Phaser FightScene, fighters, spritesheets, choreography, VFX, health bars, hit stop, camera shake, audio | pose recognition, damage math, Convex |

- VISION outputs `CaptureOutput { pose: PoseResult, photo: Blob }`.
- MULTIPLAYER stores the submission, resolves the round when both are in, emits `CombatResult`.
- GAME receives a `CombatResult` and only **presents** it. It never changes HP.

### 5.1 React integration seams (how the pieces mount together)

MULTIPLAYER owns the app screens and mounts the other two systems as React components:

```tsx
// exported by VISION from apps/web/src/features/vision/index.ts
<CaptureScreen
  onCapture={(output: CaptureOutput) => void}   // fires once after countdown + classification
  countdownSeconds={3}
  debug={false}
/>

// exported by GAME from apps/web/src/game/index.ts
<FightPlayer
  result={combatResult}                          // CombatResult
  onComplete={() => void}                        // called when the cinematic is done
/>
```

Both components must be **self-contained**: no Convex hooks inside VISION or GAME. Both must be
safe to unmount at any time (stop camera tracks, destroy Phaser game).

### 5.2 Where the shared contracts live

**`packages/backend/convex/shared/contracts.ts`** — types and constants only.
- Convex functions import it relatively: `import type { CombatResult } from "./shared/contracts";`
- Web code imports it as `import type { PoseResult } from "@posefighter/backend/convex/shared/contracts";`

It is the only file that all three workstreams read and nobody but the tech lead edits.

### 5.3 SSR: client-only code

TanStack Start renders on the server first. MediaPipe and Phaser touch `window`/`document`/WebGL.

- Mark the debug and gameplay routes as client-only: `createFileRoute("/room/$code")({ ssr: false, ... })`.
- Additionally, dynamically import heavy libs inside `useEffect`:
  `const Phaser = await import("phaser")` / `const { PoseLandmarker, FilesetResolver } = await import("@mediapipe/tasks-vision")`.
- Never reference `window` or `navigator` at module top level in a route file.

## 6. Shared contracts (canonical copy: `packages/backend/convex/shared/contracts.ts`)

```ts
type Fighter = "BOXER" | "SAMURAI" | "WIZARD";
type Move = "PUNCH" | "BLOCK" | "DODGE" | "HEAVY_ATTACK" | "SPECIAL";

interface PoseResult {
  move: Move;
  confidence: number;        // 0..1
  power: number;             // 0..100  — small damage modifier, never overrides strategy
  metrics?: { extension?: number; balance?: number; speed?: number };
}

interface CaptureOutput { pose: PoseResult; photo: Blob }   // VISION → MULTIPLAYER

interface CombatPlayerResult {
  playerId: string; nickname: string; fighter: Fighter;
  move: Move; power: number;
  damageReceived: number; hpBefore: number; hpAfter: number;
  posePhotoUrl?: string;
}

type CombatOutcome = "P1_HIT" | "P2_HIT" | "BLOCKED" | "DODGED" | "CLASH" | "DOUBLE_HIT" | "STALEMATE" | "KO";

interface CombatResult {                                    // MULTIPLAYER → GAME
  roundNumber: number;
  player1: CombatPlayerResult;
  player2: CombatPlayerResult;
  outcome: CombatOutcome;
  winnerPlayerId?: string;                                  // set on KO
  animationSequence?: string[];                             // optional hints; GAME may ignore
}

const MAX_HP = 100; const COUNTDOWN_SECONDS = 3; const ROOM_CODE_LENGTH = 4;
```

### 6.1 Semantics
- `player1` is always the room host (seat 1); `player2` is the joiner. Presentation places P1 on the left.
- `outcome` is neutral: `P1_HIT` means **player1 took damage**.
- `KO` overrides any other outcome; `winnerPlayerId` is then set.
- `power` ranges 0–100 and produces a damage multiplier of 0.85–1.15 (see GAME_DESIGN.md).

### 6.2 Fixtures
Every workstream must have fixtures matching these types. Canonical example fixtures are in
`docs/agents/GAME.md` → "Fixture examples". Copy them; don't invent different shapes.

### 6.3 Character configuration (GAME-internal, documented for visibility)
`CharacterDefinition` (id, name, assets, animations, effects) lives in
`apps/web/src/game/characters/`. It is **not** shared; only GAME depends on it. `FightScene` must
never contain character-specific frame logic; everything comes from the definition.

### 6.4 Contract change process
1. Write the proposed diff under "Contract change requests" in `docs/HACKATHON.md` (who, what, why).
2. Tell the other two devs in chat. Two 👍 = approved.
3. Tech lead (or the requester with approval) edits `contracts.ts` on `main` in a single commit.
4. Everyone rebases. Prefer **adding optional fields** over renaming.

## 9. MVP — the ONLY definition of done

Two different phones open the deployed app.
1. Player 1 creates a room and sees a code. Player 2 joins with it.
2. Both pick nickname + fighter and reach CHOOSE YOUR MOVE.
3. Both perform a pose; it is captured and classified on-device.
4. Both lock a move. **Neither can see the other's move early.**
5. Both phones receive the same resolved round.
6. Both see the two real pose photos, then FIGHT!, then the same animated fight.
7. Both see the same HP change. Next round begins.
8. Someone reaches 0 HP → KO → winner screen.

## 13. Mobile-first requirements (everyone)

- Portrait-first layout, `100dvh`, safe-area insets, buttons ≥ 56px tall, no hover-only interactions.
- `touch-action: none` / `overscroll-behavior: none` on capture and fight screens.
- iOS Safari: `getUserMedia` requires **HTTPS** (or localhost); `<video>` needs `playsInline muted autoplay`;
  audio only starts after a user gesture; the camera stream must be stopped on unmount.
- Test on a real phone via tunnel or Vercel preview every 30 minutes, not just at the end.

## 14. Visual direction

Not a SaaS app. Anime · arcade · neon · high contrast · dramatic condensed typography · huge VS screen ·
chunky health bars · flash frames · screen shake · particles. Real pose photos are the stars of the reveal;
the contrast "ridiculous real photo → epic animated fight" is the whole joke. Dark background by default
(`<html class="dark">` is already set).
